# hand_eye — SO-101 클릭 Pick & Place

Depth 카메라 화면에서 물체를 클릭하면 SO-101 팔이 집어서 옮긴다.
그러려면 **카메라 좌표 → 로봇 좌표** 변환(hand-eye)과 **팔 기구학**이 둘 다 맞아야 한다.
이 폴더는 그 둘을 잡고, 검증하고, 실제로 집는 것까지를 담는다.

실기 구성 (실측 확인함)

| | |
|---|---|
| 카메라 | Orbbec Astra Pro (VID 0x2BC5 / PID 0x060F), 640x480 @ 27fps, 최소거리 약 60cm |
| | Orbbec SDK v2 미지원 모델 → OpenNI2 런타임 + primesense 바인딩으로 접근 |
| | 화면용 영상은 **IR** 을 쓴다. depth 와 같은 센서라 픽셀이 1:1 대응하고 정렬 보정이 필요 없다 |
| 로봇 | SO-101, Feetech STS3215 x6, COM18 @ 1Mbps, 12.2V |

## 2. 실행하면 벌어지는 일

시작하면 캘리브레이션 상태부터 확인한다. 따로 스크립트를 먼저 돌릴 필요가 없다.

```
[1/2] 팔 캘리브레이션: arm_calib.json 이 없습니다.
      지금 설정할까요? (Y/n) >          ← 있으면 "다시 설정할까요? (y/N)"

[2/2] 카메라-로봇 캘리브레이션: handeye.json 이 없습니다.
      탁상 위에서 실제로 집을 수 있는 위치 4곳 이상을 등록해야 합니다.
      지금 잡을까요? (Y/n) >            ← 있으면 "다시 잡을까요? (y/N)"
```

창이 뜨면 **홈 자세로 이동**한 뒤 대기한다. 팔이 어디에 있었는지 모르는 채로 첫 클릭을 받으면 경로를 예측할 수 없기 때문이다.

### 키

| 키 | 동작 |
|---|---|
| `q` | 종료 | 
| `h` | 홈 자세 |
| `o` / `c` | 그리퍼 열기 / 닫기 |
| `r` | 상태 리셋 |
| `d` | 보기 전환 — 화면 우상단 `VIEW:` 버튼 클릭과 같다 (아래) |
| `w` | 집기 가능 영역 표시 ON/OFF |
| `s` | 현재 프레임 저장 |
| `k` | hand-eye 캘리브레이션 모드 토글 |
| `t` | 토크 ON/OFF (손으로 팔 움직이기) |

### 보기 모드 — `d` 키 또는 화면 우상단 `VIEW:` 버튼

| 모드 | 화면 | 클릭 |
|---|---|---|
| `SENSOR` | 정렬 모드: 컬러 + 도달가능영역 오버레이 / 비정렬: IR 영상 (기본) | **가능** — depth 와 픽셀이 1:1 |
| `DEPTH` | depth 컬러맵을 겹침 | **가능** — 같은 좌표계 |
| `COLOR` | 정렬 모드: 오버레이 없는 순수 컬러 (같은 정렬된 피드 재사용) / 비정렬: 별개 UVC 렌즈 | 정렬 모드 **가능** / 비정렬 **막힘** — 보기 전용 |

도달 가능 영역 표시는 컬러 모드에서 그리지 않는다 (depth 화소 위에 그리는 것이라
겹칠 수 없다).

### depth_align — depth 를 컬러 좌표계로 하드웨어 정렬

**기본으로 켜져 있다.** 끄려면 `$env:DEPTH_ALIGN='0'`.

드라이버(OpenNI2 `IMAGE_REGISTRATION_DEPTH_TO_COLOR`)가 **공장 D2C 파라미터로
depth 를 컬러 격자에 투영**한다. ros_astra_camera 의 `depth_align` 과 같은 것이고,
그 코드도 `use_uvc_camera=true`(= Astra Pro) 일 때 이 기능을 막지 않는다.

이 모드에서는:

- 화면이 **컬러**가 된다 (IR 스트림은 끈다 — 정렬 대상이 아니고 USB 대역만 먹는다)
- 컬러에서 클릭한 픽셀이 **곧 depth 화소**다. `ALIGN` 호모그래피가 필요 없다
- 뷰 순환의 COLOR 모드는 카메라를 새로 열지 않고 이 정렬된 피드를 그대로 쓴다 —
  SENSOR 와 같은 화면이지만 도달가능영역 오버레이가 빠진 순수 컬러이고, 정렬돼
  있으니 그대로 클릭할 수 있다
- 역투영을 **컬러 렌즈 기준**으로 한다 (`COLOR_FX`, 기본 615px ≈ HFOV 55°).
  IR 기준 579.9px 를 그대로 쓰면 6% 스케일 오차가 그대로 들어간다

> **hand-eye 를 다시 잡아야 한다.** IR 기준으로 잡아 둔 `handeye.json` 은 좌표계도
> 내부파라미터도 다르므로 그대로 쓸 수 없다. 시작할 때 콘솔이 그렇게 알려준다.

**실기 검증 결과** (Astra Pro, 640x480)

| 항목 | 결과 |
|---|---|
| 정렬 적용 여부 | depth 가 실제로 워핑됨 — 스케일 0.943, 중앙 15px / 모서리 32px 이동 |
| depth+컬러 동시 | **30.3 fps** (컬러 첫 프레임 6.2s 뒤) |
| 화면이 진짜 컬러인가 | 평균채도 34 (depth 컬러맵 폴백이면 120) |
| 정렬 정확도 | 컬러 엣지↔depth 엣지 거리: **항등 4.89px** < 워프 5.96 < 역워프 5.98 |
| 교차검증 | 비정렬 depth 는 워프를 걸어야 맞음 (3.60px < 항등 5.45px) — 정렬이 정확히 그 차이를 없앤다 |
| 방법 타당성(대조군) | IR↔비정렬 depth 는 항등이 최소(1.64px) — 채점 방식이 옳다 |

**중요한 함정**: 컬러 첫 프레임을 받기 **전에** depth 를 읽으면 depth 읽기가 컬러
협상을 굶겨서 컬러가 영영 안 온다(그리고 멈춘 것처럼 보인다). 그래서 여는 순서가
`정렬 ON → 컬러 시작 → 첫 컬러 프레임 대기 → 그 다음부터 depth 읽기` 다.
`ALIGN_COLOR_TIMEOUT`(기본 10초) 안에 컬러가 안 오면 **자동으로 정렬을 끄고 IR 로
되돌린다** — 멈춘 채로 남지 않는다.


컬러는 **depth 와 같은 Astra 장치**의 것을 써야 한다. Astra Pro 의 컬러는 depth 와 별개의
UVC 인터페이스(`VID_2BC5`)로 붙어 있고, 노트북 내장 웹캠과 같은 목록에 섞인다.

**번호는 못 믿는다.** OpenCV 는 카메라를 번호로만 받는데, DirectShow 가 매기는 그 번호는
Windows 장치 목록 순서와 다르고 USB 를 다시 잡을 때마다 바뀐다. 실제로 같은 날 아침에
index=1 이 Astra 였다가 오후에 노트북 웹캠이 되어 있었다. IR↔컬러 장면 매칭도 시도했지만
두 영상의 밝기 특성이 달라 내부점이 4개 대(같은 장면)와 0개(다른 장면)로 차이가 작아
단독 판단 근거로는 약하다.

그래서 순서는 이렇다:

1. `color_cam.json` 에 저장된 번호 (사람이 고른 것)
2. `$env:COLOR_CAM_INDEX`
3. 장면 매칭이 **뚜렷한 승자**를 낼 때 그 번호
4. Windows 장치 목록에서 Orbbec VID 로 센 번호

**결정타는 화면의 `CAM n` 버튼**이다. 누를 때마다 다음 번호로 바꿔 열고, 맞는 화면이
나올 때까지 누르면 그걸로 끝이다. 다음 실행부터 자동으로 그 카메라를 연다.

- 없는 번호(카메라가 2대인데 2번)에 걸리면 **다음 번호로 알아서 넘어간다**. 빈 번호에서
  막히지 않는다
- 저장은 **실제로 열린 번호만** 한다. 없는 번호가 저장되면 다음 실행이 매번 실패한다

(OpenCV 빌드에 OBSENSOR 백엔드가 있으면 장치를 스스로 찾으므로 이 문제가 없다.
이 PC 의 OpenCV 5.0 에는 그 백엔드가 없다.)

**카메라는 별도 스레드가 연다.** UI 스레드에서 직접 열고 읽으면 화면이 멈춘다 —
장치를 찾느라 PowerShell 을 부르고(수백 ms), DSHOW 초기화에 2초 넘게 걸리고,
Astra 는 USB2.0 한 대역을 depth/IR 과 나눠 써서 `read()` 가 길게 막히기 때문이다.
UI 는 '가장 최근 프레임'만 잠깐 잠그고 가져가므로 기다리는 일이 없다
(모드 전환 0.3ms, 프레임 가져오기 0.4ms).

**대역은 장치가 열린 뒤에 넘긴다.** depth 를 재우는 시점이 중요하다:

- 컬러 모드로 바꾸자마자 재우면 → 여는 동안(1.5~3초) 화면이 정지 화면으로 굳어
  '멈춘 것' 처럼 보인다
- 끝까지 안 재우면 → depth 가 USB 대역을 다 먹어 컬러 프레임이 영영 안 온다

그래서 **장치가 실제로 열린 순간**에 재운다. 여는 동안에는 센서 영상이 계속 흐르고,
굳어 있는 구간은 '열림 ~ 첫 프레임' 약 1초뿐이다. 그동안 `컬러 카메라 여는 중...` 을 띄우고,
8초간 프레임이 없으면 포기하고 SENSOR 로 되돌린다(대역도 즉시 돌려준다).
컬러 모드를 나가면 장치를 닫고 depth 를 깨운다. 해상도는 640x480 으로 고정한다.

후보 카메라를 하나씩 열어보는 장면 스캔은 **기본으로 하지 않는다**(`$env:COLOR_SCAN='1'`).
카메라 하나 열고 닫는 데만 몇 초가 걸리는데 IR↔컬러 매칭이 4점 대 0점 수준이라
그 시간을 들일 만큼 믿을 수 없다 — CAM 버튼 한 번이 더 빠르고 확실하다.

자동 검출이 틀리면 `$env:COLOR_CAM_INDEX` 로 번호를 직접 지정한다.
REST 의 `/get_rgb` 는 보기 모드와 무관하게 **항상 depth 와 정렬된 영상**을 준다 —
받은 픽셀을 그대로 `/pick` 에 넘길 수 있어야 하기 때문이다.

## 3. 좌표계와 기구학

로봇 베이스 기준 `(x, y, z)` [m]. **TCP = 그리퍼 파지점**(lerobot 이 쓰는 `gripper_frame_link` 와 동일).

치수는 공식 URDF([TheRobotStudio/SO-ARM100](https://github.com/TheRobotStudio/SO-ARM100) `Simulation/SO101/so101_new_calib.urdf`)에서 관절 origin 을 체인으로 곱해 뽑았다.

| 상수 | 값 | 의미 |
|---|---|---|
| `L_SHOULDER_R` | 30.39mm | pan 축 → shoulder_lift 축 **수평 오프셋** |
| `L0_BASE_H` | 116.60mm | 베이스 바닥 → shoulder_lift 축 높이 |
| `L1_UPPER` | 116.00mm | shoulder_lift → elbow_flex |
| `L2_FORE` | 135.00mm | elbow_flex → wrist_flex |
| `L3_WRIST` | 159.42mm | wrist_flex → 그리퍼 파지점 (평면 성분) |

> 이 상수로 만든 평면 3링크 모델은 URDF 전체 체인(회전행렬 포함)과 무작위 300자세에서 **최대 0.017mm** 차이다.

**주의 두 가지**

- shoulder_lift 축은 pan 축 바로 위가 아니라 **30.4mm 앞**이다. 이 오프셋은 pan 과 함께 돌기 때문에 hand-eye 변환으로 절대 흡수되지 않는다 — 모델에 없으면 계속 30mm 씩 틀린다.
- 링크 평면은 pan 축에서 18.3mm 옆으로 비켜 있지만 **그리퍼 파지점은 다시 중심선으로 돌아온다.** 그래서 평면 3링크 모델로 계산해도 맞는다.

### 영자세 (모든 관절 0도)

**링크가 일직선인 자세가 아니다.**

```
A1_ZERO = 90°   위팔 수직
A2_ZERO =  0°   아래팔 수평 (위팔과 직각)
A3_ZERO =  0°   그리퍼는 아래팔과 일직선
→ 이 자세의 TCP = (324.8, 0, 232.6) mm
```

직각자 하나로 확인되는 자세라서 이걸 0도로 삼았다. 링크를 앞으로 쭉 편 수평 자세로 착각하면 관절마다 70도 넘게 어긋난다.

서보 가동범위의 **한가운데**(= URDF `so101_new_calib` 의 영자세)는 이 자세가 아니라 위팔 76.03° / 아래팔 2.21° / 손목 −2.84° 자세다. 그 차이를 `MIDRANGE_Q` (lift −13.97° / elbow +16.18° / wrist −5.05°) 로 두고 환산한다.

## 4. 팔 캘리브레이션 (`calibrate_arm.py` = test4 의 5b 절)

전 과정 **토크 OFF**. 팔은 손으로 잡고 진행하며, 중력으로 처지니 받쳐야 한다.

| 단계 | 내용 |
|---|---|
| 1 | **관절 min/max 리밋** — `[k]`유지 / `[s]`손으로 훑어 측정 / `[t]`직접입력. `ik_to_count()` 의 하드 클램프가 된다 |
| 2 | **부호 + 영점** — 부호를 먼저 재고, 영점은 `[r]`가동범위 중앙에서 계산(권장) 또는 `[p]`자세를 손으로 잡아 측정 |
| 3 | **실시간 TCP 확인** — 손으로 움직이며 링크 길이까지 통과한 좌표를 눈으로 본다 |
| 4 | **테이블 접촉 검사** — 그리퍼를 테이블에 대면 TCP z 가 0 이어야 한다 (±10mm) |
| 5 | **HOME 왕복 검사** — 목표 → 카운트(클램프) → TCP 를 다시 계산해 차이를 본다 (전송 없음) |

`[r]` 을 권장하는 이유: URDF 영자세의 정의가 "각 관절 가동범위의 중앙"이라, 1단계에서 양쪽 끝까지 훑었다면 그 중앙이 곧 영점이다. 사람이 자세를 잡지 않으니 눈대중 오차가 없다.

**3~4 단계가 핵심이다.** 서보각만 봐서는 영점이 틀린 것을 알 수 없고, 그 상태로 hand-eye 까지 가면 카메라를 의심하며 시간을 버린다.

## 5. hand-eye 캘리브레이션

### 점 모으기 (`k` 또는 시작 마법사)

1. 그리퍼 끝을 탁상 위 한 지점에 정확히 댄다
2. 화면에서 **그 지점**을 클릭한다
3. 콘솔에서 Enter — 로봇 좌표는 그 순간 실측된다

**4곳 이상**, 넓게 퍼뜨리고 높이도 섞을 것(전부 같은 평면이면 변환이 불안정하다). 점이 모자라면 `k` 를 다시 눌러도 캘리브레이션 모드가 유지된다.

점을 찍을 때마다 기존 점과 대조해 즉시 경고한다. **강체변환은 거리를 보존하므로, 두 점 사이 거리가 카메라와 로봇에서 다르면 그 점이 잘못된 것이다** — 이 지표는 해를 구하기 전에, 알고리즘과 무관하게 데이터만으로 판정된다.

### 패널

```
tx ty tz [mm] / roll pitch yaw [deg]   ± 버튼, 스텝 1·5·20mm / 0.2·1·5°
클릭 지점 → 로봇좌표 / 실제 팔 TCP / 오차 + dx dy dz
테이블면 검증: 기울기 · z평균 · 실측 카메라 높이   [평면정렬]
[점추가] [자동풀기] [이상점버림] [비우기]
[검증] [점 저장] [점 읽기] [표시 ON/OFF]
[저장(handeye.json)] [파일에서 다시읽기]
불일치 최대 xx mm (n번) / 평면두께 xx mm      ← 풀기 전에 데이터 상태
```

- **자동풀기** — Kabsch 로 풀고 `handeye.json` + `handeye_points.json` 에 **바로 저장**한다. 화면·두 파일이 항상 같은 해를 가리킨다
- **검증** — 저장된 점으로 실제 이동해 "그때 그 자세"가 재현되는지 본다. 그리퍼는 닫지 않는다
- **점 읽기** — `counts` 가 있으면 지금의 기구학으로 로봇좌표를 **다시 계산**한다. 링크 상수나 영점을 고쳐도 점을 다시 찍을 필요가 없다
- **이상점버림** — 가장 어긋난 점 하나를 버린다

### 손으로 조절하는 경우 (6개 값)

점을 4개 이상 찍을 수 있으면 `자동풀기` 가 항상 낫다. 손 조절은 마지막 몇 mm 를 다듬거나 카메라를 살짝 건드렸을 때만.

| 증상 (서로 떨어진 3곳 이상에서 확인) | 조절할 값 |
|---|---|
| 어디서든 dx·dy·dz 가 같은 값 | `tx/ty/tz` — 화면의 값을 그대로 |
| z 만 일정하게 틀림 / 테이블면 z평균 ≠ 0 | `tz` |
| 테이블면 기울기 ≠ 0 | `평면정렬` 버튼 (roll/pitch/tz 한 번에) |
| 먼 쪽으로 갈수록 z 가 틀어짐 | `pitch` |
| 좌우로 갈수록 z 가 틀어짐 | `roll` |
| 왼쪽·오른쪽에서 dy 부호가 반대 | `yaw` |

이동은 화면의 `dx dy dz` 를 그대로 누르면 된다. **회전은 지렛대만큼 증폭된다** — 카메라에서 테이블까지 약 600mm 이므로 **1° ≈ 10mm**, 최소 스텝 0.2° ≈ 2mm. 순서는 `평면정렬 → yaw → tx/ty → tz`.

## 6. 동작 (pick / place)

관절을 **한 개씩** 움직인다. 나갈 때는 `pan → lift → elbow → wrist_flex → wrist_roll`, 돌아올 때는 그 반대로 접는다.

```
pick                                   place
1. 그리퍼 열기                          1. 놓을 위치 위로     (펴는 순서)
2. 목표 위에서 정렬   (펴는 순서)        2. 놓는 높이까지 하강 (펴는 순서)
3. 하강              (펴는 순서)        3. 놓기 ← 표면 위 50mm
4. 파지                                4. 후퇴              (접는 순서)
5. 들어올림          (접는 순서)        5. 그리퍼 닫기
6. 홈 복귀 (문 채로) (접는 순서)        6. 홈 복귀           (접는 순서)
```

- 전체 시퀀스를 **미리** 도달 가능성 검사한다(`check_steps`). 물건을 문 채 중간에 멈추지 않기 위함
- 화면에서 붉은 영역 = 집기 불가, 초록 경계선 = 작업영역 경계
- 한 관절씩 움직이면 손끝이 직선으로 가지 않는다. 실측 이탈량: 접근→하강 70mm, 파지→들어올림 92mm, 들어올림→홈 45mm. 물체를 건드릴 것 같으면 3·5번만 동시 이동으로 되돌리면 된다

## 7b. REST API — 원격에서 좌표로 집기

마우스 클릭과 **같은 개념, 같은 코드 경로**다. 화면 픽셀 `(x, y)` 를 주면 그 지점의
depth 로 로봇좌표를 만들어 집거나 놓는다. 판단·실행은 `App.command()` 한 곳에서만
하므로 마우스와 REST 가 어긋나지 않는다.

| 요청 | 뜻 |
|---|---|
| `GET /pick?x=320&y=240` | 그 픽셀의 물체를 집는다 (손이 비어 있어야 함) |
| `GET /place?x=420&y=300` | 그 픽셀 위치에 내려놓는다 (물고 있어야 함) |
| `POST /pick` `{"x":320,"y":240}` | 위와 동일 (JSON 본문) |
| `GET /get_state` | 지금 무엇을 하는 중인지 (아래 표) |

```bash
curl "http://127.0.0.1:8765/pick?x=320&y=240"
curl -X POST http://127.0.0.1:8765/place -H "Content-Type: application/json" -d "{\"x\":420,\"y\":300}"
curl "http://127.0.0.1:8765/status"
```

응답은 **접수까지**다. 동작 완료는 `/status` 로 확인한다 — 팔이 움직이는 몇 초 동안
HTTP 를 붙잡고 있으면 클라이언트가 타임아웃 후 재시도해서 같은 동작을 두 번 건다.

```json
{"ok": true, "message": "집는 중... (0.200,-0.000,0.010)",
 "action": "pick", "uv": [320, 240], "depth_m": 0.4,
 "estimated_depth": false, "target_base_mm": [200.0, -0.0, 10.0]}
```

거부되면 `409` 와 사유가 온다: 좌표가 화면 밖 / depth 없음 / 도달 불가 / 동작 중 /
hand-eye 미보정 / 이미 물고 있음(pick) / 물고 있지 않음(place) / 캘리브레이션 중.
좌표 형식이 틀리면 `400`, 없는 경로는 `404`.

동시 요청은 락으로 하나만 접수된다(4개를 동시에 던져도 1개만 접수되고 나머지는
"동작 중입니다"). 좌표는 **창 왼쪽 카메라 영상 기준**이며 오른쪽 조절 패널은 제외다.

### 상태 확인 — `GET /get_state`

`/status`, `/state` 도 같은 응답이다.

| `state` | `label` | 뜻 |
|---|---|---|
| `waiting_pick` | 잡기 기다림 | 손이 비었고 명령 대기 |
| `picking` | 잡는중 | pick 시퀀스 실행 중 |
| `waiting_place` | 놓기 기다림 | 물체를 물고 명령 대기 |
| `placing` | 놓는중 | place 시퀀스 실행 중 |
| `homing` | 홈 복귀중 | 시작 시 / `h` 키 |
| `busy` | 동작중 | 그 외 작업 (그리퍼, 검증) |
| `calibrating` | 캘리브레이션중 | 이 동안 pick/place 는 거부된다 |
| `not_calibrated` | 미보정 | hand-eye 가 없어 pick 이 거부된다 |

내부 모드(IDLE/HOLDING/BUSY)만으로는 "잡는중"과 "놓는중"을 구분할 수 없다. BUSY 는
그저 '워커가 뭔가 하는 중'이라, 무슨 작업인지는 `Job.kind` 로 따로 추적한다.

```json
{"ok": true, "state": "picking", "label": "잡는중",
 "mode": "BUSY", "busy": true, "holding": false,
 "calibrating": false, "handeye_calibrated": true,
 "status": "집는 중... (0.200,-0.000,0.010)",
 "last_error": null, "points": 6,
 "image_size": [640, 480], "tcp_mm": [200.0, 0.0, 10.0], "arm": "FeetechSO101Arm"}
```

`states` 필드에 전체 상태 목록과 한글 라벨이 같이 온다 — 클라이언트가 문자열을 따로
관리할 필요가 없다. `last_error` 는 마지막으로 실패한 작업의 사유다(없으면 `null`).

**원격 루프는 이렇게 돈다**

```python
while True:
    s = requests.get(f"{api}/get_state").json()["state"]
    if s == "waiting_pick":
        requests.get(f"{api}/pick",  params={"x": x1, "y": y1})
    elif s == "waiting_place":
        requests.get(f"{api}/place", params={"x": x2, "y": y2})
    elif s in ("picking", "placing", "homing", "busy"):
        time.sleep(0.3)          # 동작 중 - 기다린다
    else:
        break                    # not_calibrated / calibrating - 사람이 개입할 차례
```

### 영상 가져오기

| 요청 | 응답 |
|---|---|
| `GET /get_rgb` | 카메라 영상 JPEG. `?format=png` 무손실, `?overlay=1` 마커·배너까지 그린 화면 |
| `GET /get_depth` | **16bit PNG, 단위 mm** (무손실). 받은 쪽에서 `png/1000.0` 하면 그대로 미터 |
| `GET /get_depth?format=color` | 사람이 보는 용도의 컬러맵 JPEG (값은 못 읽는다) |
| `GET /get_depth?x=320&y=240` | 그 화소의 depth·카메라좌표·로봇좌표·집기 가능 여부 (JSON, **팔은 안 움직인다**) |

응답 헤더에 `X-Image-Size`, `X-Depth-Unit: mm`, `X-Depth-Filled-Px`(메운 화소 수),
컬러맵일 때는 `X-Depth-Min-Mm` / `X-Depth-Max-Mm` 이 실린다.

```bash
curl -o rgb.jpg    "http://127.0.0.1:8765/get_rgb"
curl -o depth.png  "http://127.0.0.1:8765/get_depth"       # 16bit mm
curl "http://127.0.0.1:8765/get_depth?x=320&y=240"
```

```python
# 원격에서: 영상 받아 → 좌표 정해 → 그 지점 확인 → 집기
import cv2, numpy as np, requests
api = "http://192.168.0.10:8765"
rgb   = cv2.imdecode(np.frombuffer(requests.get(f"{api}/get_rgb").content, np.uint8), cv2.IMREAD_COLOR)
depth = cv2.imdecode(np.frombuffer(requests.get(f"{api}/get_depth").content, np.uint8),
                     cv2.IMREAD_UNCHANGED).astype(np.float32) / 1000.0   # [m]
x, y = 320, 240
print(requests.get(f"{api}/get_depth", params={"x": x, "y": y}).json())   # 집을 수 있는지 먼저
print(requests.get(f"{api}/pick",      params={"x": x, "y": y}).json())
```

`/get_depth?x=&y=` 로 먼저 확인하면 `pick` 을 던져 보고 409 로 알아낼 필요가 없다.
좌표계는 `/get_rgb` 와 `/get_depth` 와 `/pick` 이 모두 같다 — 받은 영상의 픽셀 그대로 쓰면 된다.

### 테스트 클라이언트 — `api_client.py`

REST 를 눈으로 확인하는 GUI. 표준 tkinter + 이미 쓰는 cv2/numpy 만 쓴다
(tkinter 를 고른 이유는 한글이 제대로 보여서다 — cv2 창은 한글을 네모로 그린다).

### LLM 클라이언트 — `llm_client.py`

REST 6개를 **스킬**로 등록하고, Gemini Robotics-ER 이 하나씩 골라 부르게 한다.
좌표 규약은 이 저장소의 다른 VLM 코드(`test3.py`)와 같은 **[y, x] 0~1000 정규화** 이고,
클라이언트가 실제 픽셀로 바꿔서 REST 에 넘긴다. 화면 크기가 바뀌어도 프롬프트는 그대로다.

```
pip install google-genai pydantic          # 이 두 개가 더 필요하다
$env:GEMINI_API_KEY='...'
python hand_eye/llm_client.py                          # 웹 UI 로 지시 (기본)
python hand_eye/llm_client.py "주황색 통을 상자에 넣어"    # 첫 지시만 미리 주기
python hand_eye/llm_client.py --cli                    # 터미널로 지시
python hand_eye/llm_client.py --auto "..."             # 실패해도 안 묻는다
```

**지시는 웹으로 받는다.** 실행하면 `http://127.0.0.1:8770` 이 열린다(`--port`, `--host`,
`--no-browser`). 페이지는 stdlib `http.server` 하나로 서비스하고, 브라우저가 0.6초마다
`/poll?since=N` 로 새 로그·화면·질문만 받아 간다.

```
로봇 조종  [잡기 기다림]  [생각 중 3/12]      ← 상태는 test4 의 /get_state 를 되물어 온다
┌ 현재 화면(/view.jpg) ─┐ ┌ 재시도 질문 [예, 다시 해봐] [아니오] ┐
│                      │ │ 진행 로그                            │
└──────────────────────┘ └──────────────────────────────────────┘
[무엇을 시킬까요? ______________] [보내기] [화면 다시 보기] [종료]
```

에이전트는 메인 스레드에서 돌고(다음 지시를 큐에서 기다린다) HTTP 는 데몬 스레드가 받는다.
둘 사이는 **큐 하나와 Event 하나**로만 만나므로, 웹이 끊겨도 진행 중인 동작은 그대로 끝난다.
`--cli` 를 주면 예전처럼 터미널 `input()` 으로 받는다 — 두 방식은 같은
`log / set_view / set_status / next_order / ask` 다섯 가지만 구현한 클래스라 나머지 코드는 같다.

| 스킬 | REST | 비고 |
|---|---|---|
| `get_state` | `/get_state` | 상태를 보고 pick/place 중 무엇이 가능한지 판단 |
| `get_rgb` | `/get_rgb` | 화면을 다시 본다. `llm_view.jpg` 로 저장돼 사람도 같은 그림을 본다 |
| `get_depth_at` | `/get_depth` | **팔을 움직이지 않고** 그 점의 깊이·로봇좌표·집기 가능 여부만 확인 |
| `pick` / `place` | `/pick`, `/place` | 접수 후 `/get_state` 를 폴링해 동작이 끝날 때까지 기다린다 |
| `wait` / `say` / `done` | — | 대기 / 한마디 / 지시 종료 |

동작 방식:

- 시작하면 `/get_rgb` 로 한 장 받아 **무엇이 보이고 무엇을 시킬 수 있는지** 를 먼저 말한다
- **pick/place 는 묻지 않고 바로 실행한다.** 실패했을 때만 웹에서 `[예, 다시 해봐]/[아니오]` 를 묻고,
  최대 3번(`MAX_RETRY`)까지 같은 지점을 다시 시도한다. `--auto` 면 그것도 묻지 않는다
- 실패가 확정되면 그 결과를 모델에 돌려준다 — 모델은 다른 지점을 고르거나 `done` 을 부른다
- **지시 하나가 끝나면 화면을 새로 받고 다음 지시를 기다린다.** 명령줄로 지시를 준 경우에도
  끝나고 종료하지 않는다. `화면 다시 보기`(=`r`), `종료`(=`q`) 버튼은 그냥 그 글자를 지시로 보낸다
- 5분(`ASK_TIMEOUT`) 안에 재시도 질문에 답이 없으면 '아니오' 로 보고 진행한다 — 브라우저를
  닫아 두고 자리를 비워도 프로그램이 거기서 멈춰 있지 않는다
- 한 지시당 스킬 호출은 `MAX_STEPS`(12) 로 막는다 — 모델이 같은 실패를 맴돌지 않게

## 7. depth 처리

- **구멍 메우기** (`fill_depth_holes`) — 유효 이웃의 평균으로 가장자리에서 안쪽으로 번져 들어간다(9x9 창, `DEPTH_FILL_MAX_PX` 화소까지). 큰 구멍의 한가운데는 일부러 안 채운다. 처리 4.5~13ms/프레임
  - 평평한 곳: 평균 1.5mm / 작은 반점: 정확 / **50mm 단차 경계: 최대 41mm 틀림**
  - 메운 화소는 **청록색**으로 표시하고 커서 정보에 `[추정]`, 캘리브레이션 클릭 시 콘솔 경고
- **앞면 샘플링** (`sample_depth(near=True)`) — 캘리브레이션 클릭은 창 안에서 가장 앞면 무리만 골라 median 한다. 얇은 그리퍼를 클릭했을 때 뒤쪽 테이블 거리가 잡히는 것을 막는다

## 8. 안전장치

| 장치 | 내용 |
|---|---|
| 속도/가속 제한 | 토크를 켜기 **전에** 건다. `goal_speed=0` 은 무제한 최고속이라 빼먹으면 첫 명령에 팔이 튄다 |
| 낡은 목표 덮어쓰기 | 연결 시 서보의 Goal_Position 을 현재 위치로 덮어쓴 뒤 토크를 켠다 (실측 최대 55° 튐 방지) |
| 분할 전송 | 관절당 8°씩 나눠 보낸다 |
| 부하 감시 | 이동 중 서보 부하가 한계를 넘으면 그 자리에 정지 |
| 안전 상자 | `WS_R [80, 250]mm`, `WS_Z [5, 240]mm` + IK 도달성 |
| `tcp_sanity` | 팔이 테이블면보다 30mm 넘게 아래를 보고하면 점 수집을 거부하고 영점 재캘리브를 안내 |
| 토크 정리 | `finally` + `atexit` 로 이중 보장 |

**캘리브레이션 여유** — 영점이 조금 틀어져 있으면 그리퍼를 테이블에 댔을 때 z 가 음수로 나온다. 그 값을 거부하면 정작 영점을 고칠 점을 못 모으므로, 캘리브레이션 경로에 한해 **z 를 −30mm 까지 허용**한다(`CALIB_Z_TOL`). 집기 동작은 종전 그대로 +5mm 바닥이다.
